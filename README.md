# KOXPilot

**出海达人营销投前决策智能体**

> 把一句话投放 brief，变成一份可执行、可追责、带预算分配和风险证据链的达人投放清单，并用可复现的实验说清这份清单比"凭粉丝量选人"少浪费多少钱——以及这个结论有多稳。

**方式一：本地起，两条命令**（不依赖任何外部服务，最稳）

cd web && pnpm install && pnpm run prepare-data && pnpm run dev   # → http://localhost:5173

## 这个项目在解决什么问题

出海达人营销（KOL / KOX）的钱，很大一部分浪费在**投前**：

达人自称做 3C，实际内容在做美妆；粉丝 200 万但互动率 0.3%，一眼买粉；受众 80% 在印尼，而你要投沙特。这些问题在投放后看数据能发现，但钱已经花了。行业里最朴素的做法是**按粉丝量降序选人直到花完预算**——本项目把它作为对照基线，实测在 $245,000 预算下，这种做法有 **32.5% 的钱花在了水号和高风险达人身上**。

KOXPilot 做的事：在签合同之前，把"这个达人能不能投、值多少钱、为什么"算清楚，并且**每个结论都能点开看到证据**——命中了哪条规则、实际值多少、同组阈值多少。

不是"AI 帮你选人"，而是**"AI 告诉你为什么不选他，以及不选他省了多少钱"**。

## 30 秒看懂

```
一句话 brief
   ↓  A1 BriefAgent      自然语言 → 结构化 CampaignSpec（LLM）
   ↓  A2 RecallAgent     5,000 达人库 → 定向候选池（规则）
   ↓  A3 GateAgent       四层质量门禁 G0→G1→G2→G3（规则 + 动态分位数阈值）
   ↓  A4 FitAgent        语义适配打分（正式链路=规则版；LLM 版在构建期真调、仅作离线对照，理由见下）
   ↓  A5 BudgetAgent     带硬约束的预算分配（规则 + 贪心修补）
   ↓  A6 AuditAgent      成本审计 + 反事实价值审计
投放清单 + 预算分配 + 风险证据链 + "比基线多省了多少钱"
```

### 业务价值：卖的不是"多赚多少"，是"少烧多少"

先说结论，包括不利于我自己的那部分。

三个 campaign 合计 $245,000 预算，对照"按粉丝量降序选人"的行业朴素基线：

| | 单次实测（seed 20270919） | **12 种子稳健区间** |
| --- | --- | --- |
| 少浪费占预算 | −32.5%（$79,719） | **−21.5% ± 13.7%**（95% CI 12.8%~30.2%） |
| 有效曝光 | +98.6% | **+97.3% ± 54.6%** |
| 跑输基线的种子数 | — | **1/12（总口径）** |
| 选中达人数 | 基线 18 人 → KOXPilot 181 人 | — |
| 硬约束满足 | 3/3 campaign 全部满足 | 全部种子均满足 |

**那个 32.5% 是 12 个种子里第 2 高的观测，落在均值的 95% CI 之外。** 方向可信（11/12 为正，p=2.0e-4），但幅度被单次采样高估了约 50%。追加的 24 种子复核进一步降到 **19.1% ± 18.6%**，说明 21.5% 可能仍然偏乐观。我把这个数字写在这里，而不是继续挂着好看的 32.5%。

> 24 种子那组数不在入库产物里（`output/multiseed.json` 存的是 12 种子那份）。要复核就跑 `make multiseed SEEDS=24`，纯确定性、跑得出一样的值；注意它会**覆盖**那份 12 种子产物，跑完用 `make multiseed` 还原。判据与逐项结论见 [`docs/06` §7](./docs/06-robustness.md)。

浪费金额与有效曝光**全部按 ground truth 计算，不使用引擎自己的分数**——否则就是自己给自己打分。

#### 这 21.5% 里，门禁到底占多少？

"少浪费"这件事里混着两个原因：**不把钱压在少数头部大号上**（结构分散化）和**识别水号并按质量排序**（门禁）。为了把它们拆开，加了一条第三臂 `diversified_no_gate`：与基线同一个候选池、强制 KOXPilot 的分层/地域/单人配额、但排序只看"每美元名义曝光"，**全程不读门禁判定与真实性折扣**。于是 `总差额 = (第三臂 − 基线) + (KOXPilot − 第三臂)`：

| 12 种子 · 少浪费金额 | mean ± std | 为负的种子 |
| --- | --- | --- |
| 合计 | $52.7k ± $33.4k | 1/12 |
| 其中**门禁与质量排序** | **$40.0k ± $12.6k**（CV 0.31） | **0/12** |
| 其中结构分散化 | $12.6k ± $39.0k（CI 跨 0） | **4/12** |

**稳定的那一段是门禁，不是分散投放**——而定稿单种子上看起来正好相反（分散化 $56.2k vs 门禁 $23.5k），我原本的猜测被自己的数据推翻了。三条必须一起说的反面事实：① 第三臂的**绝对**有效曝光在 12/12 个种子上都高于 KOXPilot，**而且把花费归一化之后它照样赢**——这件事我单独写成下面一节，不放在这里用一个分句稀释掉；② 第三臂平均选 **516 人**，真实采购里不可执行，它只是对照臂不是方案；③ "门禁贡献"其实是"门禁过滤 + 质量排序"的合计，两者共用同一批分数，不再拆得开。详见 [docs/06 表 1 附](docs/06-robustness.md)。

#### ⚠️ 第三臂在主指标上打赢了我

我自己跑出来的第三臂在主指标上打赢了我，这里如实摆出来。**每美元有效曝光**是我自己选定的主口径（契约里写着前端主对比只许用 `effective_views_gt_per_dollar` 与 `waste_usd`），在这个口径上 `diversified_no_gate` 三条 brief 全胜，没有一条例外：

| brief | 每千美元有效曝光 · KOXPilot | 只分散不门禁 | 差距 | 按粉丝量基线 |
| --- | --- | --- | --- | --- |
| BRIEF-001 | 56,749 | **83,664** | **+47.4%** | 11,964 |
| BRIEF-002 | 63,359 | **93,454** | **+47.5%** | **64,848** |
| BRIEF-003 | 50,769 | **73,125** | **+44.0%** | 24,230 |

数字来自 `output/audit.json → counterfactual_value_audit.per_campaign`，服务 `/api/plan` 的 `allocation.arms` 是同一批值。

**它为什么赢，说清楚。** 不是它作弊，也不是指标不公平——这个指标是我自己定的。原因有两层：一是它把同一笔钱极度摊薄到微达人身上（三条 brief 分别选 **228 / 122 / 166** 人，我是 69 / 39 / 73），微达人的 CPM 便宜得多，单位曝光自然更便宜；二是**门禁会挡掉一部分"便宜且名义曝光高"的号**——数据不完整的、真实性存疑的，第三臂全程不读门禁判定，这些库存它照买，我不买。于是我为更干净的库存付了更高的单价。这就是价差的来源。

**那么真正的取舍是什么。** 拿 BRIEF-001 并排看这笔单价买到了什么：

| | KOXPilot | 只分散不门禁 |
| --- | --- | --- |
| 浪费金额 / 占预算 | **$2,175 / 2.72%** | $14,599 / **18.25%** |
| 名单里的水号个数 | **2** | **41** |
| 品牌安全高风险号 | **0** | **4** |
| 花在门禁会直接 reject 的人身上 | **$0** | **$12,390** |
| 要签、要沟通、要交付的合约数 | **69 份** | **228 份** |

三条 brief 上第三臂分别买了 **4 / 2 / 4** 个品牌安全高风险号（我是 **0 / 0 / 0**），分别把 **$12,390 / $5,180 / $14,564** 花在门禁会直接判 reject 的达人身上。所以结论只能这么写：**门禁买的是确定性和品牌安全，不是每美元曝光效率的上限。** 我这套东西的上限就摆在那儿——想要每美元曝光最高，别用它。

**谁因此变好了。** 这一层我先前的版本没答，只顾着自证技术指标：

- **品牌方**：不用在投放结束后解释"为什么我们的品牌出现在争议内容旁边"（0 个高风险号 vs 4 个），也不用为 41 个水号的曝光付款——18.25% 的预算打水漂在结算时是要有人签字认下来的。
- **投放执行的同学**：69 份合约和 228 份合约是两种工作量。228 个微达人的报价、寄样、脚本审核、发布确认、结算，在真实代理公司里基本排不进档期。这条臂的效率是在假设"合约签署与沟通成本为零"的前提下算出来的，而这个成本不在我的指标里——所以我也不能拿它去反驳第三臂，只能把它标成"我这个指标没度量的东西"。
- **边界坦白**：如果一个投放方的 KPI 真的只有每美元曝光，且品牌安全与水号曝光都不重要（比如纯拉新的效果广告、事后按转化结算），**那我这套东西不该被采用**，应该直接用第三臂那种"最大化分散度"的策略。我做的是把不确定性和品牌风险压下去，这件事只有在"翻车有代价"的场景里才值钱。

**BRIEF-002 上还有一处对我更不利的细节，我不省略。** 那条 brief 上我的浪费金额 **$5,494（12.21%）比第三臂的 $3,695（8.21%）还高**，有效曝光率也更低（**87.11% vs 91.55%**）。说明我的门禁在那条 brief 的定向下**没有起到应有的作用**——3 个水号进了最终名单，这是个真实的待改进项，不是口径问题。而且同一条 brief 上按粉丝量基线的每千美元有效曝光是 **64,848**，也比我的 63,359 高，浪费金额只有 **$376（0.84%）**。所以"我们至少稳定赢按粉丝量基线"这句话在 BRIEF-002 上也不成立，我不写那句。这条 brief 上我唯一站得住的事实是买入库存的干净程度：基线把 **$44,624** 花在门禁判"需人核"的人身上，我是 $0。

**一个还没做的下一步。** 这两条臂的策略并不互斥：**先用门禁过滤掉 review/reject，再在干净池子里最大化分散度**（而不是像现在这样按质量加权价值排序），理论上可能同时拿到干净和效率。我没有实现它，也没有它的实验数据——写在这里是为了标明方向，不是成果。

#### 但真正的价值不在均值，在方差

同一实验量化了另一件事：**基线是高方差赌博。**

| | 基线（按粉丝量选人） | KOXPilot |
| --- | --- | --- |
| 浪费率 std（36 个观测） | **33.6%** | **4.7%**（小 7.2 倍） |
| 有 25% 的局，浪费率 | **> 50%**（最惨一局 99.9%） | **从未超过 14.8%** |
| 有 42% 的局，浪费率 | < 5%（抽到好牌） | — |

决定性的证据：KOXPilot 输的那几局，基线的浪费率都 ≤ 5.6%（本来就没踩坑，没什么可省）；而基线爆掉的 9 局里，KOXPilot **9/9 全胜**。

一处必须自己先说清的统计口径：上表的 36 是 **12 种子 × 3 campaign 的观测数，不是 36 次独立试验**——同一种子下的三个 campaign 共享同一个达人库，属于伪重复。所以我不用合并后的 F 检验 p 值（2.7e-21，自由度被高估、量级不可当真），而是报**独立单位（种子）上的检验**：三个 campaign 各自 n=12，方差比 p 分别为 **1.5e-07 / 1.3e-08 / 1.2e-06**，F 值 51.6 / 81.8 / 34.9。加上不依赖分布假设的极端频次计数（9/36 vs 0/36）与条件胜率，才是这个结论的证据。判据与限定写在 `output/multiseed.json → B_variance_attribution.independence_unit`。

所以这套东西的产品价值不该翻译成"帮你多赚 21.5%"，而是：**把"四分之一的概率烧掉一半预算"这个尾部风险，换成稳定的约 4% 浪费。** 代价是在基线本来就抽到好牌的局里小输一点。对一个毛利率只有 2.63% 的投放代理业务来说，消灭尾部灾难比提高均值更值钱。

门禁能力本身则高度稳定，不依赖种子：fraud F1 **0.7275 ± 0.0090**、AUC **0.8878 ± 0.0054**、三分类准确率 **0.6679 ± 0.0051**（CV ≤ 0.023）。**波动来自"基线只选 5 个人"的极小样本对照臂，不是来自模型能力。**

#### 顺带一个不利于自己的发现

单种子报出的弱项清单里，只有 `follower_bucket = mega` 是跨种子稳定的系统性短板（11/12 个种子进榜，p=1.5e-07）；`country = SA` 与 `platform×bucket = youtube|macro` 是**采样噪声**（p=0.132 / 0.803）。

这是典型的 winner's curse：**单次实验里"最差的那几格"，大部分只是运气差，不是真短板。** 完整数据见 [docs/06-robustness.md](docs/06-robustness.md) 与 `output/multiseed.json`（`make multiseed`，纯确定性，约 30s 可复跑）。


### 该不该用大模型：用实验回答，不用立场回答

同一批 600 样本、同一 ground truth、唯一变量是 system prompt：

| 方案 | Precision | Recall | F1 | token |
| --- | --- | --- | --- | --- |
| 规则对照组（20 行 Jaccard 规则） | 0.419 | 0.857 | **0.562** | **0** |
| Prompt v1 朴素版 | 0.237 | 0.845 | **0.363** | 434,018 |
| Prompt v2 加负例约束 | 0.355 | 0.786 | **0.489** | 467,327 |
| Prompt v3 定义业务判据（生产版） | 0.614 | 0.798 | **0.691** | 492,460 |
| 最优单组合 v3 × Azure | 0.688 | 0.786 | **0.733** | — |

**前两版 Prompt 都输给了零成本的规则基线。** 只有 v3 反超，而 v3 的关键改动不是加咒语、不是给更多例子，是把判据从「标签是否一致」改写成「**投放方按 declared 选人会不会选错**」——从技术口径改成业务口径。

这张表的形状（先输后赢）本身就是结论：**能写 prompt ≠ 会写 prompt，差别在于有没有把业务判据想清楚。**

> ⚠️ 诚实记录一处混淆变量：v3 同时改了两件事（判据业务化 + 品类邻接表从举例改为完整注入），v2→v3 的增益无法严格归因到单一改动。详见 [docs/04-prompt-and-cost.md](docs/04-prompt-and-cost.md)。

### 真实成本账

`output/llm_bench.json`，全部取自各 API 返回的 `usage` 字段，**非估算**：

172 次调用 · 总 token **1,103,473**（其中 reasoning token **403,202**）· 平均 6,415 token/次 · 耗时 939s · 相对全 LLM 方案调用量缩减 **3.95×**。

其中 1 个 batch 调用失败，按"未覆盖"处理（该模型覆盖率记为 0.98），**没有用默认值填充冒充成功**。

## 四层质量门禁

门禁只能看到**可观测字段**，看不到 ground truth（这一条由 AST 静态扫描测试强制保证）。

| 层 | 判什么 | 代表规则 |
| --- | --- | --- |
| **G0 完整性** | 数据够不够做判断 | 关键字段缺失率、报价缺失、受众地域缺失 |
| **G1 真实性** | 是不是水号 | 互动率偏离同组分位数、粉丝增长突刺 vs 自然爆红、评论机器人特征、播放/粉丝比异常 |
| **G2 一致性** | 自称与实际是否对得上 | 标签错配、三源标签冲突、受众地域/语言与 campaign 目标错配 |
| **G3 品牌安全** | 能不能让品牌露脸 | 高风险内容、争议历史、竞品合作、受管制品类资质 |

### 一个设计要点：阈值是分组标定的，不是全局固定的

TikTok 的 nano 达人和 YouTube 的 mega 达人，互动率基线天然差一个数量级。用一个全局阈值判"互动率异常"，等于系统性地冤枉一类人、放过另一类人。

所以阈值按 **(platform × follower_bucket) 分 25 组**、在库内标定分位数（`output/thresholds.json`）。证据链里输出的不是"互动率 0.4% 偏低"，而是"**互动率 0.4%，低于 tiktok|macro 组 p10 的 1.2%**"——这句话投放方能直接拿去和达人对质。

## 前端和后端是怎么连的（先把这件事说清楚）

这个问题值得单独一节，因为答案不是"前端调后端 API"这么一句话就说完的：线上**同时**跑着两条通道，而且它们的结果被逐条对撞。

```
Python 核心链路（src/koxpilot/）
   │  终端跑 make all，固定种子 SEED=20270919
   ▼
data/*.json + output/*.json          ← 真实计算产物，已入库
   │                                    │  构建期：web/scripts/prepare-data.mjs 派生
   │ api/build_bundle.py 复制进 _bundle  ▼
   ▼                                 web/public/data/*.json（11 个）
通道 A：Python FastAPI 服务              │
   api/ 直接 import src/koxpilot        ▼
   A1→A6 全链路真算                   通道 B：TS 引擎在浏览器里把门禁和预算再算一遍
   4 个端点，见 api/CONTRACT.md          src/engine/（~1,500 行）+ src/budget/（~1,100 行）
```

**通道 A 是真服务，不是壳。** `api/koxpilot_service/` 不重写任何业务逻辑，它 import 的是 `src/koxpilot` 里那份被 768 个测试盯着的代码：门禁走 `gates.engine.evaluate`，预算走 `budget.planner.plan_campaign`，审计走 `eval.audit.counterfactual_report`，证据句走 `gates.humanize`。接口契约冻结在 `api/CONTRACT.md`（4 个端点：`/api/health`、`/api/plan`、`/api/kox/{id}/explain`、`/api/gate/batch`），默认公开、无需 token。本地起服务后就能拿 curl 验（`api/run.sh` 是部署平台生成的启动脚本，只在平台上跑；本地用下面这条）：

```bash
pip install -r api/requirements.txt
cd api && python3 main.py        # → http://127.0.0.1:8000
curl -s http://127.0.0.1:8000/api/health
curl -s http://127.0.0.1:8000/api/kox/KOX-000002/explain
```

这个 `explain` 的每一句理由，和你在本地跑 `python -m koxpilot.cli explain KOX-000002` 打出来的**逐字相同**——因为两边调的是同一个 `gates/humanize.py`，不是两处各写一份文案。这件事由 `api/check_cli_parity.py` 逐字符断言，不靠我自己眼看。

**`scope`：自证"参与计算的候选一条没被裁"。** 契约升到 [v1.1](./api/CONTRACT.md)（`engine_version` 1.1.0）后，`/api/plan` 的响应里多了一个只读的 `scope` 块，四个字段就是为了让人不用信我：`recall_total`（命中定向的人数）/ `computed_on`（真正进门禁与预算计算的人数，**必须等于 `recall_total`**）/ `detail_rows`（这次返回多少条候选明细）/ `truncated_for_compute`（恒为 `false`，为 `true` 就说明服务与离线 CLI 在算两道题）。BRIEF-001 现在返回 `recall_total 746 / computed_on 746 / detail_rows 60 / truncated_for_compute false`——**裁掉的只是给前端看的 60 条明细，746 个候选一条不少地参与了计算**。这个字段是上一条 bug（见下方自我修复清单第 14 条）的直接产物：光把代码改对不够，得让"有没有被裁"变成响应里可查的事实。

顺带一条本地布局的实测：把 `api/_bundle/` 整个移走（模拟评审 clone 下来、手上没有部署产物的情形），`cd api && python3 main.py` 仍然跑通，BRIEF-001 照样返回 69 人 / $79,855.29 与上面那组 `scope` 值。原因是路径解析写的是「`api/_bundle` 优先、回落仓库根」（`api/koxpilot_service/paths.py`），两种布局都成立。

**通道 B 也不是放录像。** `src/engine/` 与 `src/budget/` 是四层门禁与预算分配的**独立第二实现**——服务没连上时它独立跑完全流程，功能不缺项；服务在线时它就变成一台**校对机**：`/api/plan` 会在 `parity_payload.verdicts` 里把这次召回集里每个达人的判定都带回来，浏览器对同一批 `kox_id` 现算一遍，界面直接显示比对条数与差异条数。

于是"0 差异"这件事有了两层证据：构建期全库 5,000 条的离线比对（下一节），以及**运行期**每次点击的实时比对。两者都是两套独立写出来的实现互撞，不是同一份代码自己跟自己比。

代价与边界照旧写在明处：

| 能力 | 通道 A（Python 服务） | 通道 B（浏览器） |
| --- | --- | --- |
| A2 召回 / A3 四层门禁 / A5 预算分配 / A6 审计 | ✅ 真算，复用核心链路 | ✅ 真算，独立第二实现 |
| A1 brief 解析 | ✅ 探到可用凭据就**真调 LLM**；凭据缺失/被拒/超时即回落规则版，`parse_path` 标明走的哪条、`brief.notes` 逐字写明降级原因 | ⚠️ 只有规则版 |
| A4 语义适配 | ⚠️ 构建期真调后固化，正式链路用 `rule_fit_score` | ⚠️ 同左 |
| 数据集 | 同一份 `kox_5000.json`，两侧 `dataset_sha256` 相同 | 同左 |

**为什么两条通道都留着，而不是砍掉一条。** 砍掉 A，A1 就永远只有规则版、也没有"服务端真跑"这回事；砍掉 B，就失去了唯一能证伪 A 的东西。留着两条，代价是我得保证它们不漂移——这正是 `make api-parity` 每次要跑的事。

## 前后端双实现一致性

前端不是读一份预先算好的静态结果来演戏。四层门禁在**浏览器里用 TypeScript 重新算一遍**，和 Python 版读同一份阈值表（TS 侧不做任何再标定）。

每次 `pnpm run refresh` 会把 TS 引擎对全库 5,000 条的判定与 Python 的 `output/verdicts.json` 逐条比对，结果落盘到 `web/public/data/consistency.json`，页面直接读取：

```
total 5000 · matched 5000 · diff_count 0 · match_rate 1.0
比对字段：verdict / group_key / rules[] / completeness / authenticity / consistency / brand_safety / fraud_score
```

**这个数字是脚本生成的，不是写死在组件里的。** 改坏任一侧实现，`refresh` 就会红。

## 我自己抓到并修掉的问题

一个只展示漂亮指标的作品是可疑的。下表这 14 个缺陷是我自己在开发过程中发现并修掉的，其中两个是**评测自证**——ground truth 和特征其实是同一个东西的两面，于是朴素方法就能拿到近乎完美的指标。这类问题不会报错，只会给你一个漂亮得不真实的数字。

第 11–13 条是收口阶段才抓到的，属于另一类：**数字是对的、结论也是对的，但它到此为止，没有产生任何动作。** 第 14 条又是另一类：**代码没报错、结果也"看起来合理"，但服务和离线在算两道不同的题。**

> 口径说明：下表是按「**会不会被当场证伪**」挑出来的 14 条，**这张表就是唯一对外清单**。早期版本在 Demo 里另开了一个「踩过的坑」面板放**构建期自我修复日志**（当时 14 条，切分方式不同——和本表现在的 14 条**不是同一个 14**，纯属巧合）；界面收敛成 3 个页签后那个面板已经不在了，所以别再去页面上找它。那份日志里只有两条纯工程记录不在本表：一条是"两个进程并发写同一个缓存文件"导致产物被截断（已改成写临时文件再原子替换），另一条是"同 prompt 同模型两次 F1 不同"（非贪心解码，见下方 [Prompt 实验](#prompt-实验--该不该用大模型) 与 [`docs/05` §3.3](./docs/05-boundaries.md#33-单次运行的波动没有被消掉)）。两份清单交集大但不等同——**不是同一个数**，我不把它凑成一样。

| # | 问题 | 表现 | 修完的代价 |
| --- | --- | --- | --- |
| 1 | 标签错配的 ground truth 等价于"两个集合是否相交" | 规则基线 **P=R=F1=1.000** | 规则基线 F1 掉到 **0.562** |
| 2 | 观测模型是整块替换，正例 Jaccard 只有 0 和 1 两个取值 | 5 个 arm 的召回**精确相同**（0.857），尽管彼此预测差异 146/600 | 召回重新变成真实 tradeoff |
| 3 | LLM 缓存 key 只 hash `kox_id`，不 hash 内容 | 重新生成数据后旧预测被静默复用，**不报错只给错结论** | 旧缓存全部失效（正确行为） |
| 4 | 评测表里拿"库级中性 spec"去报只有具体 campaign 才有意义的指标 | 语义适配分位数**全是 1.0**，一格假装有意义的数据 | 分布恢复区分度（p10 0.20 / p50 0.65） |
| 5 | 招牌价值数字只跑了一个种子 | 32.5% 看着很硬，实际是 12 个种子里第 2 高的观测 | 改口径为 **21.5% ± 13.7%**，并承认 1/12 种子跑输基线 |
| 6 | 弱项清单没做显著性检验 | 报了 6 条弱项，实际只有 1 条是真的 | 其余定性为采样噪声（winner's curse） |
| 7 | 反事实只有两臂，"少浪费"无法归因 | "32.5% 是门禁省下来的"这句话在两臂产物上**没有证据**，差额里混着结构分散化 | 补第三臂 `diversified_no_gate` 后拆开：门禁与质量排序 **$40.0k ± $12.6k**（12/12 为正），结构分散化 $12.6k ± $39.0k（**4/12 为负**、CI 跨 0）——原来的猜测被推翻 |
| 8 | "我们用 LLM 做语义适配"这句话在正式链路里站不住 | `llm_cache.json` 有 260×3 条真实 LLM 适配分，而 `make eval` 每个数字都来自 `rule_fit_score`；文档只"承认"落差、没有任何数字，既无法验证也无法被推翻 | 补 `eval/llm_fit.py` 做量化对照：覆盖率 **14.9%**、双算率 **97.1%**、覆盖子集上 LLM 分只降不升 → 结论"继续用规则版"由判据算出（三项全过会自动翻成可升格），并真跑了注入反事实（判定只翻 1 条、合计少浪费 $735，不作为招牌数字） |
| 9 | 产物里"这些 token 是哪个模型跑的"有两个答案 | `llm_bench.models.ark` 写的是 endpoint id（`ep-2026…`），`per_task[*].model` 写的是服务端型号（`doubao-…`）；两处都叫 `model`，照着前者写材料就会说出"我们用的模型是 ep-2026…"——那是资源 id 不是模型 | 补 `llm/identity.py` 把两个概念拆成 `requested_model_id` / `served_models`，对外只报服务端型号；判据只看"名字是谁说的"，不做 `ep-` 前缀之类的模式匹配；调用全失败时如实标 `requested_id_only`。回归测试从产物现取请求 id，断言它在 `metrics.json` 里只出现在 `requested_model_id` 上 |
| 10 | 预算模型里的关键假设 `decay=0.7` 长期**没有任何证据** | `budget/policy.py` 里 `POST_DECAY_SCAN = (0.5, 0.7, 0.9)` 这个常量定义了很久、注释也承诺给三档结果，但产物里从来没有它——也就是"同一达人第 n 条内容的边际曝光衰减"这个**建模假设**（不是观测值）一直无人验证，而所有预算与反事实数字都建在它上面 | 补 `eval/decay_scan.py` 真跑三档（共用同一批 GateResult，逐档重跑三臂 + gt 审计）。结论必须两半一起说：**价值结论不依赖它**（合计少浪费离差仅 **1.4%**、两段归因符号逐档不翻转），**但选谁会变**（选中名单 Jaccard 最低 0.826、金额加权重叠最低 **0.651**，低于自设 0.8 判据）→ 判定 `value_conclusions_hold_but_selection_shifts`。且这条扫描**回答不了**"哪一档更接近真实世界"，产物里专门有字段和测试堵住这个过度解读 |
| 11 | 分好类的 `caveats` 算完就被丢掉 | `decay_scan.py` 特意把记录分成 `blockers`（会推翻结论的硬伤）与 `caveats`（不推翻结论但必须一起说的限定），源码注释还专门解释"混成一个列表就会出现'扫过了没问题'这种听起来通过、实际掩盖限定的说法"——**结果返回值里根本没有 `caveats` 这个键**。本次实测 `blockers` 为空、`caveats` 有 1 条（金额重叠 0.651 不达标），读者只会看到一片绿。与第 10 条同源：注释在替一段不存在的输出背书 | 把 `caveats` 接回产物并与 `blockers` 分列；测试断言"`selection_stable=false` 时 `caveats` 不得为空"，且两类记录不许混装 |
| 12 | 判据不达标，却没有任何**产品动作** | 第 10 条扫出 `selection_stable=false` 之后，我原本只在文档里补一句"名单会随假设变动"。这句话没错，但对使用者没用——投手拿到的仍是一份**不知道哪里靠不住**的清单，不确定性被承认了，成本全转嫁给他 | 新增 `_delivery_tiers()`：按"在几档 decay 上都被选中"把名单切两层——**核心层 162 人 / \$220,855 / 占支出 90.2%**（三档全选中，可直接下单）与**假设敏感层 19 人 / \$23,962 / 9.8%**（转人工确认，不自动执行）。结论从"名单不唯一"变成"不确定性只影响 9.8% 的预算、已定位到 19 个人"。测试钉住两层必须无损划分正式名单、金额之和必须等于实付 |
| 13 | 方差检验把 36 个观测当成 36 次独立试验 | `pooled_all_campaigns.n_obs = 36` 其实是 **12 种子 × 3 campaign**，同一种子下三个 campaign 共享同一个达人库，属**伪重复（pseudo-replication）**。伪重复高估自由度、把 p 值进一步压小，而我拿着 p=2.7e-21 当证据用 | 补 `independence_caveat` / `independence_unit`，把 pooled p 值显式标成 `pooled_p_value_usable=false`；改报**独立单位（种子）上**的逐 campaign 方差比检验（n=12，p=**1.5e-07 / 1.3e-08 / 1.2e-06**），并以不依赖分布假设的极端频次（9/36 vs 0/36）与条件胜率为主证据。原有的"有界比例致 p 偏乐观"caveat 保留，两条限定叠加 |
| 14 | **展示参数悄悄改变了计算语义**：HTTP 服务的 `_recall` 把 `options.top_n`（展示用，默认 200）当成了召回上限 | 同一条 BRIEF-001，离线 CLI 选 69 人花 **$79,855（利用率 99.82%）**，服务只花 **$5,693（7.12%）**——**预算利用率差 14 倍**。根因是被截断的池子直接进了门禁和分配器：BRIEF-001 命中定向 **746** 人，截到 200 之后，分配器的结构配额（长尾 ≥25% / 单国 ≤60% / 单人 ≤20%）在小池里**根本无可行解**，于是钱花不出去。接口不报错、响应结构完整、数字看起来也"合理"，光看结果发现不了 | 截断只作用于**展示**：`top_n` / `explain_limit` 只裁返回的候选明细条数，召回不截断。服务升 1.1.0、契约升 [v1.1](./api/CONTRACT.md)，并新增只读 `scope` 块（`recall_total` / `computed_on` / `detail_rows` / `truncated_for_compute`）把"参与计算的候选一条没被裁"写进响应体。`src/koxpilot/` **一行未改**——错的一直只是服务层那一次切片 |

第 14 条给我的教训值得单独记一句：**"展示参数悄悄改变了计算语义"这类 bug，只有把两条路径的中间量逐个对齐才能发现，看结果对不对是发现不了的。** 服务返回的清单、金额、约束检查全都是自洽的，`all_enforced_satisfied` 甚至是 `true`——只有把服务和 CLI 的**候选池条数**摆在一起，才看出一边 746 一边 200。所以修法不只是改那一行切片，而是把中间量（`recall_total` / `computed_on`）提成响应里的一等字段：**下次再出这种事，它得自己露出来。**

修复的代价是数字全面变差，我照实采用：

| 指标 | 早期 | 最终采用 |
| --- | --- | --- |
| 规则基线 F1 | 1.000 | **0.562** |
| 少浪费金额 | $104,239（42.5%） | **$79,719（32.5%）** |
| 有效曝光提升 | +133.6% | **+98.6%** |
| 阈值敏感性最大 F1 偏移 | 0.0523（不稳健） | 0.0582（**仍不稳健**） |

最后一条：±20% 阈值扰动下最大 F1 偏移 0.0582，按我自己设的判据（≤0.05 才算稳健）**是不达标的**。我没有把判据放宽到 0.06 让它变绿——改判据等于改考卷。

完整过程见 [docs/03-evaluation.md](docs/03-evaluation.md) 的「反自证」专章。

### 代码级保证

- **AST 静态扫描测试**：遍历 `gates/` `budget/` `llm/` 的所有源文件，断言不存在对 `gt` / `true_categories` / `is_fraud` / `fraud_type` 等字段的任何访问。门禁想作弊，测试先红。
- **泄漏哨兵测试**：断言朴素 Jaccard 规则的 F1 必须 < 0.95，且正例的 Jaccard 分布不得退化成双峰。
- **文档数字防漂移测试**（`tests/test_doc_numbers.py`）：本文件里的招牌数字——F1 / AUC / 少浪费金额与占比 / 95% CI / 两段归因 / 方差与极端频次 / 分层交付人数金额 / PromptBench 四个 F1 与 token / 调用次数——逐条对到 `output/*.json` 的具体字段上，**格式也按人眼看到的那串字符断言**。产物重跑后数值变了而这里的字没跟着改，测试就红。
  写这条测试的起因是我发现原来这段写着一句站不住的话：「没有一个数字是手写进文档的」。数字当然是手打进 markdown 的，它们只是**来源**于产物；真正的风险恰恰是产物变了、文档不会自己改。这个项目已经在同一个毛病上栽过两次（`POST_DECAY_SCAN` 的注释替一段不存在的输出背书、`decay_scan` 的 `caveats` 算完没进产物），所以这次不改口气、改机制。
- 全套 **768 个测试**，覆盖数据可复现性、门禁判定、反泄漏、预算约束、评测指标、多种子、价值归因、decay 分层交付、模型标识、HTTP 接口契约、端到端冒烟。

## 已知弱项（没有藏在末尾）

经 12 种子稳健性实验区分了**系统性短板**与**采样噪声**——这个区分很重要，前者说明设计有短板（可改进），后者不该当成结论：

| 弱项 | 单种子数值 | 跨种子性质 |
| --- | --- | --- |
| `follower_bucket = mega` 水号识别 | F1 **0.467**（P 0.342 / R 0.737） | ✅ **系统性短板**（11/12 种子进榜，delta −0.197，p=1.5e-07）。头部达人样本少、互动率天然偏低，与买粉特征混淆 |
| `country = SA` | F1 0.476（P 0.833 / R 0.333） | ⚠️ **采样噪声**（p=0.132），不构成结论 |
| `platform × bucket = youtube\|macro` | F1 0.476 | ⚠️ **采样噪声**（p=0.803），不构成结论 |
| 阈值敏感性 | ±20% 扰动最大 F1 偏移 **0.0582** | 判定为**不稳健**，未达自设的 0.05 判据 |
| 标签错配存在**召回天花板** | — | 部分正例的观测被 bio 完全带偏，只看 declared + observed 无法检出。要突破必须引入第三方信号（实际带货商品类目、评论语义） |
| 反事实价值的**幅度不稳** | 单次 32.5% | 12 种子 21.5% ± 13.7%（其中 1/12 个种子跑输基线）；24 种子复核 19.1% ± 18.6%（其中 3/24 跑输） |
| 结构分散化的贡献**不显著** | 单次看起来占 70% | 12 种子 $12.6k ± $39.0k、4/12 为负、CI 跨 0；稳定的那一段是门禁与质量排序（$40.0k ± $12.6k） |
| 投放**名单不唯一** | — | `decay` 是建模假设。三档扫描下价值结论稳（离差 1.4%），但选中名单金额加权重叠最低 **0.651**——换个假设就换一批人。对此产品的动作是**分层交付**（见下），不是一句免责声明 |
| **BRIEF-002 上门禁没起到应有作用** | 3 个水号进了最终名单，浪费 **$5,494（12.21%）** | ❗**真实待改进项**：这条 brief 上我的浪费率高于只分散不门禁臂（8.21%）、也高于按粉丝量基线（0.84%），有效曝光率 87.11% 是三臂最低。不是口径问题，是那条定向下 G1 没抓住（见[上面那节](#️-第三臂在主指标上打赢了我)） |
| A1 这次实测**没走 LLM 路径** | `/api/health` 里 `llm_runtime.available` 是 `true`，但真调用被网关拒绝：HTTP **403 `model is not allowed`** | 凭据存在、该模型不被允许调用，A1 因此落到规则解析。降级原因由服务逐字写进 `brief.notes` 而不是吞掉；换一份有权限的凭据就会走 LLM 路径——这是环境权限问题，不是功能没做 |

反向扫描 45 个合格分层，只有 1 个系统性短板 + 1 个"轻微但一致"（`country = BR`）。**换句话说，我单种子那份弱项清单里大部分是运气差，不是真短板**——这正是 winner's curse。

#### 当判据不达标时，产品该做什么

上面那条"名单不唯一"值得单独说，因为它暴露的是产品问题而不是统计问题：敏感性判据判了 `selection_stable = false`，如果我只在文档里补一句"名单会随假设变动"，投手拿到的仍然是一份**不知道哪里靠不住**的清单——不确定性被承认了，但成本全转嫁给了使用者。

所以我给它接了一个降级路径：按"在几档 decay 上都被选中"把名单切成两层。

| 交付层 | 人数 | 参照档金额 | 占比 | 动作 |
| --- | --- | --- | --- | --- |
| **核心层**（三档全选中） | **162** | **$220,855** | **90.2%** | 可直接下单，入选不依赖 decay 取值 |
| 假设敏感层（仅部分档位选中） | 19 | $23,962 | 9.8% | 标记"重复触达折扣假设敏感"，转人工确认或改按单条采购，不自动执行 |

结论因此从"名单不唯一"变成一句可执行的话：**这个假设的不确定性只影响 9.8% 的预算，且已经定位到具体 19 个人**。产物见 `output/metrics.json → budget_decay_sensitivity.delivery_policy`（含逐 campaign 的人员与金额区间），判据由 `tests/test_decay_delivery_tiers.py` 钉住（两层必须无损划分正式名单、金额之和必须等于实付）。

模型对比数字均为**单次实测值**，不是均值±方差——推理模型默认非贪心解码，实测同配置两次 F1 有 0.653 vs 0.681 的波动。结论层面（v3 > v2 > v1、LLM > 规则）是稳的，小数点后第二位不稳。

## 工程边界

| 环节 | 性质 |
| --- | --- |
| 达人数据 | **合成数据**，5,000 条，固定种子可复现。真实达人数据涉及商业敏感与隐私 |
| 四层门禁 / 预算分配 / 评测 | **确定性计算**，无 API key 即可完整复跑 |
| brief 解析 / 标签错配判定 | **构建期真调 LLM**，结果固化进 `output/llm_cache.json`；线上服务探到可用凭据时 A1 实时真调、凭据缺失/被拒/超时回落规则版（`parse_path` 写明本次走的哪条，`brief.notes` 写明降级原因），浏览器通道只有规则版 |
| 语义适配打分（A4） | **正式链路走规则版 `rule_fit_score`**；LLM 版真调过、只作离线对照。不升格的三条判据（覆盖率 14.9% / 双算率 97.1% / 覆盖子集上只降不升）由 `eval/llm_fit.py` 现算，落在 `metrics.json.table_6_llm_vs_rule.semantic_fit_llm_vs_rule` |
| 前端门禁引擎 | **浏览器内实时计算**（TypeScript），与 Python 版逐条比对 0 差异；服务在线时它同时充当运行期校对机 |
| 线上 HTTP 服务（`api/`） | **复用 `src/koxpilot`**，不重写业务逻辑；契约冻结于 `api/CONTRACT.md`，默认公开、业务错误一律 HTTP 200 + `ok:false` |

**合成数据能证明什么**：方法论、工程完整度、评测严谨度、能否发现自己的错误。
**不能证明什么**：真实分布下的绝对指标。这一点我不打算含糊。

详见 [docs/05-boundaries.md](docs/05-boundaries.md)。
